# Архитектурное решение по трейсингу

## Анализ системы и проблемные точки

**Критические места для отслеживания:**

| Компонент       | Проблемные зоны                      | Данные для трейсинга                          |
|-----------------|--------------------------------------|-----------------------------------------------|
| Online Shop API | Создание заказа, загрузка 3D-модели  | ID заказа, временные метки, параметры модели  |
| CRM API         | Подтверждение заказа, смена статусов | ID заказа, статус подтверждения, пользователь |
| RabbitMQ        | Доставка сообщений, потеря сообщений | ID сообщения, источник, получатель            |
| MES API         | Расчет стоимости, этапы производства | ID заказа, время расчета, оператор            |
| Базы данных     | Запросы статусов, обновления         | Время выполнения, ошибки запросов             |

## Мотивация

**Проблемы текущей системы:**

- Заказы теряются или зависают между системами без возможности отслеживания
- Сообщения в RabbitMQ могут теряться, создавая разрывы в процессах
- Невозможно определить, на каком этапе находится конкретный заказ
- Длительное время диагностики проблем (часы вместо минут)

**Что даст компании внедрение трейсинга:**

- Полная видимость пути заказа через все системы
- Сокращение времени поиска проблем с часов до минут
- Улучшение SLA за счет быстрого реагирования на сбои

**Технические метрики, которые улучшатся:**

- MTTR (Mean Time To Resolution)
- Обнаружение потерь сообщений в очередях
- Время диагностики инцидентов

## Предлагаемое решение

**Технологический стек:**

- OpenTelemetry для инструментации приложений
- Jaeger для сбора и хранения трейсов
- Grafana для визуализации и анализа

**Архитектурная схема:**

**Новые компоненты (выделены красным на схеме):**

- OpenTelemetry Agent на каждом сервисе
- Centralized Tracing Collector
- Jaeger Backend для хранения трейсов
- Tracing UI в Grafana

**Доработки существующих систем:**

- Инструментация Java-сервисов через OpenTelemetry Java Agent
- Инструментация C# MES через OpenTelemetry .NET SDK
- Модификация RabbitMQ для трейсинга сообщений
- Добавление trace_id во все межсервисные коммуникации

## Компромиссы

**Ограничения трейсинга:**

- Проприетарные компоненты MES требуют дорогостоящей доработки для полной инструментации
- Высоконагруженные эндпоинты могут требовать выборочного трейсинга для сохранения производительности
- Полное трейсинг всех операций создает значительный объем данных (до 100ГБ/месяц)

**Технические компромиссы:**

- В начальной версии трейсинг MES расчетов будет ограниченным
- Некоторые legacy-компоненты могут остаться без полной инструментации
- Кардинальность атрибутов ограничена для избежания проблем с производительностью

**Области, где трейсинг не принесет пользы:**

- Статические ресурсы и CDN-контент
- Фоновые задачи с низким приоритетом
- Системы, планируемые к замене в ближайшие 6 месяцев

## Безопасность

**Внутренняя безопасность:**

- Многофакторная аутентификация для доступа к системе трейсинга
- Ролевая модель доступа:
    - "Поддержка" - просмотр трейсов заказов
    - "Разработчики" - доступ к техническим деталям
    - "Администраторы" - полный доступ к системе
- Шифрование персональных данных в трейсах (адреса, телефоны, ФИО)

**Внешняя безопасность:**

- Система трейсинга доступна только из корпоративной сети
- VPN-доступ для удаленных сотрудников с двухфакторной аутентификацией
- Белый список IP-адресов для доступа к API трейсинга
- Сертификаты с ограниченным сроком действия для внешних интеграций

**Защита данных:**

- Автоматическое удаление трейсов старше 90 дней
- Аудит всех операций доступа к системе трейсинга
- Изоляция продакшн-данных от сред разработки

**Мониторинг безопасности:**

- Алёрты на подозрительную активность в системе трейсинга
- Журналирование всех действий администраторов
- Регулярный обзор прав доступа и привилегий
- Резервное копирование конфигураций безопасности
