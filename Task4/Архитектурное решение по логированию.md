# Архитектурное решение по логированию

## Анализ системы и планирование логирования

### Системы для сбора логов

- **Online Shop** - клиентские операции и заказы
- **CRM System** - управление клиентами и заказами
- **MES System** - производственные процессы и расчеты

### Список логов уровня INFO

**Online Shop:**

- Создание заказа: время, ID покупателя, номер заказа, сумма
- Загрузка 3D-модели: ID заказа, размер файла, тип модели
- Изменение статуса заказа: старый статус, новый статус, причина

**CRM System:**

- Подтверждение заказа: ID заказа, менеджер, время подтверждения
- Изменение статуса заказа: ID заказа, статус, комментарий
- Взаимодействие с внешними API: endpoint, статус, время ответа

**MES System:**

- Расчет стоимости: ID заказа, время расчета, сложность модели
- Старт производства: ID заказа, оператор, оборудование
- Изменение статуса производства: ID заказа, этап, время

**RabbitMQ:**

- Доставка сообщений: очередь, ID сообщения, статус доставки
- Обработка сообщений: потребитель, время обработки, результат

### Уровни логирования

- **INFO**: Штатные бизнес-операции и изменения состояний
- **WARN**: Нетипичные ситуации, требующие внимания
- **ERROR**: Критические ошибки, влияющие на функциональность
- **DEBUG**: Детальная информация для диагностики (включается по необходимости. DEV окружение)

## Мотивация

### Проблемы текущей системы

- Разбор инцидентов занимает часы из-за отсутствия централизованного логирования
- Невозможно отследить полный путь заказа через все системы
- Поддержка тратит время на сбор информации из разных источников
- Сложность идентификации корневых причин проблем

### Ожидаемые результаты

- Сокращение времени диагностики проблем
- Уменьшение количества эскалаций в техподдержку
- Повышение прозрачности бизнес-процессов
- Ускорение расследования инцидентов

### Технические метрики

- Время восстановления сервиса (MTTR) < 30 минут
- Полнота покрытия логами критичных операций > 95%
- Снижение времени поиска проблем с часов до минут

### Бизнес-метрики

- Сокращение количества потерянных заказов на 40%
- Повышение удовлетворенности клиентов на 35%

### Приоритезация систем для логирования и трейсинга

| Система     | Приоритет | Обоснование                                                 |
|-------------|-----------|-------------------------------------------------------------|
| MES System  | Высокий   | Критичность производственных процессов и расчетов стоимости |
| CRM System  | Высокий   | Центральная система управления заказами и клиентами         |
| RabbitMQ    | Средний   | Критичная интеграционная шина между системами               |
| Online Shop | Средний   | Первичный контакт с клиентами и создание заказов            |

## Предлагаемое решение

### Технологический стек

- **Elasticsearch** - хранение и поиск логов
- **Logstash** - обработка и трансформация логов
- **Kibana** - визуализация и анализ
- **Filebeat** - сбор логов с серверов
- **Kafka** - буферизация логов (опционально для высокой нагрузки)

### Новые компоненты

- Централизованный кластер Elasticsearch
- Ноды Logstash для обработки логов
- Агенты Filebeat на каждом сервере
- Дашборды Kibana для различных команд

### Политика безопасности

**Обработка чувствительных данных:**

- Маскирование персональных данных (телефоны, email, адреса)
- Шифрование логов при передаче и хранении
- Ограничение доступа к логам с персональными данными

**Модель доступа:**

- **Поддержка L1**: доступ к логам уровня INFO для своих заказов
- **Поддержка L2**: полный доступ к логам заказов
- **Разработчики**: доступ к техническим логам и ошибкам
- **Администраторы**: полный доступ к системе логирования

**Аутентификация и авторизация:**

- Интеграция с корпоративным SSO
- Двухфакторная аутентификация для администраторов
- Журналирование всех операций доступа

### Политика хранения

**Структура хранения:**

- Отдельные индексы для каждой системы и окружения
- Ежедневная ротация индексов для оперативных данных
- Отдельные индексы для аудит-логов и логов безопасности

**Сроки хранения:**

- Логи уровня INFO: 30 дней в "горячем" хранилище
- Логи уровня ERROR: 90 дней в "горячем" хранилище
- Аудит-логи: 1 год в "теплом" хранилище
- Архивные логи: 3 года в "холодном" хранилище

**Размеры хранилища:**

- Расчетный объем: 50-100 ГБ в день
- "Горячее" хранилище: 3 ТБ
- "Теплое" хранилище: 10 ТБ
- "Холодное" хранилище: 30 ТБ

### Система анализа логов

**Алертинг:**

- Резкий рост количества ошибок (> 5% за 5 минут)
- Зависшие заказы (статус не меняется > 1 часа)
- Аномальная активность (в 10 раз больше обычной нагрузки)
- Потеря сообщений в очередях RabbitMQ

**Обнаружение аномалий:**

- Машинное обучение для выявления нестандартных паттернов
- Автоматическое обнаружение DDoS-атак и подозрительной активности
- Корреляционный анализ событий между системами

**Интеграции:**

- Автоматическое создание тикетов при критических ошибках
- Уведомления в Slack/Telegram для ответственных команд
- Эскалация при длительном нереагировании на инциденты

### План внедрения

**Фаза 1 (1-2 месяца):** Базовая функциональность

- Развертывание OpenSearch кластера
- Настройка Filebeat на критичных сервисах
- Базовые дашборды для поддержки

**Фаза 2 (2-3 месяца):** Расширение функциональности

- Инструментация всех систем
- Настройка алертинга и уведомлений
- Интеграция с системами тикетов

**Фаза 3 (3-4 месяца):** Оптимизация

- Внедрение продвинутого анализа
- Оптимизация политик хранения
- Автоматизация реакций на инциденты
